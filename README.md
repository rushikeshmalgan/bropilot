# bro-pilot

A web app for creating AI bots and chatting with them, in early development. Each signed-in user gets a sidebar of their own bots, can create new ones (name, job, instructions), start several chats with each bot, and set up group chats with more than one bot. Bots answer with AI replies (Google Gemini) that are written by a background run, so a reply keeps going if the page is closed and shows up again when it's reopened. Bots, chats, messages and runs are saved to a Neon Postgres database. The app shell and screens follow the Figma designs.

| Computer use             | Done        | With `DAYTONA_API_KEY` set, a bot can use a desktop screen in its sandbox through one `computer` tool (screenshot, click, double click, move, type, key, scroll); every action is answered with a fresh screenshot that the model sees but nothing saves. A reply gets at most 20 screen actions and 24 model steps, with a 0.6 s pause after each action. The monitor button in a chat opens a live viewer beside it that shows the screen's state (stopped, starting, live, error), a Start button for a stopped screen, a Reload button, a notice while the bot is using the screen, Stop, and a Take control switch (view-only by default, and off while the bot is working). The viewer address is made on the server for each request, works for 5 minutes, goes only to the bot's owner, and never names the sandbox in the app's own answers. The design, threat model and open questions are in `docs/computer-use.md`. Not yet proven against the real Daytona service: whether the default image has a desktop at all, the viewer's address and port, and how well the model uses it (see `scripts/smoke-daytona.ts`) |
| Plans and usage          | Done        | `lib/plans.ts` is the one place the limits live. Free: 3 bots, no sandboxes or screen, 50 replies and 200k tokens a month. Pro: 20 bots, sandboxes and screen, 1000 replies and 5M tokens a month. Months are calendar months in UTC. A `usage` table keeps each user's replies, tokens and sandbox minutes. A reply is taken from the month's allowance in one database step before it starts, and bots are counted under a per-user lock, so requests sent at the same moment can't pass a limit; a reply's tokens are added as each model step ends (so a reply that is stopped, fails or whose chat is deleted is still counted) and its sandbox time once when it ends. A user can have at most 3 replies being written at once, and one reply may make at most 12 web lookups and use at most 200k tokens. The plan is read from the user's session when a reply is started and saved on the run (the background worker has no session); sandbox and screen tools are only offered on Pro, and creating a sandbox, starting a screen and starting a reply all check it on the server. After a downgrade, bots beyond the plan's limit (the newest ones) are kept but read-only: their chats and memory can be read, not added to or changed, and they can still be deleted. Refusals reach the screen as a plain message with an upgrade note (new bot form, chat, screen panel). The sidebar footer shows the plan and what is left. In development the plan is Free, or Pro with `BILLING_STUB_PLAN=pro`; that is ignored in production, which reads Clerk Billing with `has({ plan: "pro" })`. There is no pricing page yet |
| Durable runs             | Done        | Runs are rows in the `runs` table (`queued`, `running`, `done`, `error`, `cancelled`). The reply appears on screen as it is written: through Trigger.dev realtime when available, otherwise by reading `/api/runs/[id]` about once a second. Reloading the page picks the reply up where it is. Stop keeps the text that arrived. A 429 from the model is retried with backoff (3 attempts), a network error once, other errors not at all; a failed reply is saved with a readable message. A run that never finishes is marked failed when the chat is next opened or written to. Deleting a chat stops its run. Not yet proven against the real Trigger.dev service (see `scripts/smoke-trigger.ts`) |
| Web tools                | Done        | With `FIRECRAWL_API_KEY` set, bots get two tools: `webSearch(query, limit)` and `scrapePage(url)`. Tool calls and results are saved with the message and shown in the chat as small cards that open to show what was sent and what came back. Only public http(s) addresses can be read: local, private and link-local addresses are refused before any request, and a page that redirects to one is thrown away unread. Output is cut at 8000 characters per call. Page text is treated as data, never as instructions. A failed tool call gives the bot a short error and the reply carries on. Bots with tools get 6 steps per reply instead of 2. Without the key the tools aren't offered and the bot says it can't browse. Not yet proven against the real Firecrawl service (see `scripts/smoke-firecrawl.ts`) |
| Bot memory               | Done        | Each bot keeps small text files between chats (`bot_memory_files`). It has three tools, `memoryList`, `memoryRead` and `memoryWrite`, and the start of its `index.md` (up to 2000 characters) is put in its system prompt on every reply. Saves use a version number: a save based on an older version is refused instead of overwriting. Limits: 50 files per bot, 8,000 characters per file (what one read returns, so a bot that edits a file always sees all of it), short relative paths only (no `..`, no absolute paths). Memory is treated as notes, never as instructions. The owner can read, edit, add and delete files in the Memory tab at `/bot/[id]/settings`, opened from the sliders button in a chat's header. Because every bot has memory tools, every reply may take up to 6 model steps |
| Sandboxes                | Done        | With `DAYTONA_API_KEY` set, each bot can have its own small Linux computer with four tools: `bash(command, timeoutSeconds)`, `readFile`, `writeFile` and `listFiles`. It is created the first time a tool needs it, never earlier; a compare-and-set on `bots.sandbox_id` means two replies starting together can't create two, and a creation that died half-way is cleaned up by the next caller. Commands run as a non-root user (checked with `id -u` after creation) and no environment variables, keys or secrets are ever passed in. Limits: commands up to 120 seconds (30 by default), 90 seconds of sandbox time per reply, output cut at 8000 characters keeping its start and end, files up to 100 KB. It stops itself after 10 minutes of inactivity and starts again, with its files, on next use. The bot's settings page has a Sandbox tab with its status and a Reset button (deletes the sandbox and its files), and a Delete bot button that removes the bot, its chats, memory and sandbox. Calls appear in the chat as cards. Not yet proven against the real Daytona service (see `scripts/smoke-daytona.ts`) |
| Hardening                | Done        | Every state has one next action: no bots (make one), bots but no chat open (talk to the newest), a failed reply (a Try again button that answers the same message again and replaces the failed reply), replies or sandboxes not switched on (a plain message that names no setting), a stopped sandbox or screen (starts again, with a button), a plan limit (the message says what to do). `/api/health` is a public check (database reachable, which features are on, how many required settings are missing: no names, no user data; 503 when the database is down). Security headers on every response: `nosniff`, no framing, referrer and permissions policies, HSTS in production, and a Content-Security-Policy that is enforced only for what can't break the app (no framing, no plugins, no `<base>` tricks) while the full policy is sent as report-only until its hosts are checked in a signed-in browser (see `lib/security-headers.ts`). `lib/env.ts` lists every environment variable, and the app logs what is missing at start-up and build time without failing; `npm run check:env` prints the same by place. The screen panel opens over the chat on a phone. Abuse limits: changes (new bots and chats, memory saves, sandbox resets, deletes) 60 a minute per user, run polling 300, screen checks 120, 500 chats per user, chat request bodies 64 KB. Bot answers never show pictures (a picture's address could carry the conversation to a stranger), another bot's words in a group chat are marked as not the user's, and text that can't be stored (NUL, half an emoji) is cleaned before saving. Sign-in and sign-up were checked in a real browser, at desktop and phone width; signed-in pages were not |
| Error tracking           | Done        | With `SENTRY_DSN` set, errors from the server, the browser and the Trigger.dev worker go to Sentry; without it nothing is loaded or sent. Every event goes through a scrubber first (`lib/sentry-scrub.ts`): message text, bot memory, tool output, command output, screenshots, cookies, headers and anything shaped like an API key, token or database URL is removed, and only these are kept: the error and its stack, the route, and four tags, `userId` (the Clerk ID only), `botId`, `chatId` and `runId`. Spans time each run, each model call, each tool call (the tool's name only) and sandbox creation, and the task flushes before it exits. `app/global-error.tsx` and `app/chat/[id]/error.tsx` show a friendly page with a reference code, never the error. Source maps are uploaded only when `SENTRY_AUTH_TOKEN` exists. Checked with the real SDK and a recording transport; not yet run against a real Sentry project (`npx tsx scripts/smoke-sentry.ts` does that once a DSN is set) |
| Automated tests          | Done        | `npm test` runs the Vitest suite against the dev database: runs (retries, stop, timeouts, stuck runs, idempotent retries), the chat route and polling, web tools and URL safety, bot memory (versioned saves, limits under parallel writes), sandboxes (one per bot under parallel starts, dead-creator recovery, limits, reset, delete), computer use (the desktop's states, the screen route's access rules and limits, the tool's action limit, Stop mid-action, screenshots never saved), plans and usage (parallel requests can't pass a limit, plan resolution and the production guard, read-only bots, counting once, tools by plan), error tracking (keys, message text, memory and tool output never reach Sentry; tags, spans, flushing before exit; nothing happens without a DSN), retrying a failed reply (only the last message, only after an error, once at a time, limits still apply), the health route, environment checks and security headers, every entry point tried by another user and by nobody signed in, and the final review's findings (injection through pictures, memory and group chats, unsaveable text, per-reply and per-user limits, counting tokens as they are used, a worker's last attempt, sandbox leaks, the Sentry scrubber failing closed), ownership checks, chat logic, rate limiting and bot faces |
| Group chats              | Done        | The "New group chat" dialog saves a named chat with the chosen bots and opens it; group chats are listed in the sidebar and reopen with their messages. Start a message with `@name` to pick which bot answers; with no mention, the bot that spoke last answers |

## Running locally

Requires Node.js 20.9 or newer.

```bash
npm install
npm run dev
```

Then open <http://localhost:3000>.

Create `.env.local` before starting. It needs these variables (names only; values come from the Clerk and Neon dashboards):

| Variable                                                                                              | Used for                                         |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`                                               | Clerk API keys                                   |
| `NEXT_PUBLIC_CLERK_SIGN_IN_URL`, `NEXT_PUBLIC_CLERK_SIGN_UP_URL`                                      | Paths of the Clerk sign-in and sign-up pages     |
| `NEXT_PUBLIC_CLERK_SIGN_IN_FALLBACK_REDIRECT_URL`, `NEXT_PUBLIC_CLERK_SIGN_UP_FALLBACK_REDIRECT_URL` | Where Clerk redirects after sign-in and sign-up  |
| `DATABASE_URL`                                                                                        | Neon pooled connection string                    |
| `DATABASE_URL_UNPOOLED`                                                                               | Neon direct (non-pooled) connection string       |
| `NEON_BRANCH`                                                                                         | Neon branch the variables were pulled for        |
| `GOOGLE_GENERATIVE_AI_API_KEY`                                                                        | Google Gemini API key for bot replies (get one at <https://aistudio.google.com/apikey>) |
| `TRIGGER_SECRET_KEY`                                                                                  | Trigger.dev secret key for the environment (the Development one starts with `tr_dev_`). Needed for bot replies; copy the full key from the project's API keys page, not a masked one |
| `FIRECRAWL_API_KEY`                                                                                   | Optional. Firecrawl API key; turns on the bots' web search and page reading tools |
| `SENTRY_DSN`                                                                                          | Optional. Sentry DSN for the server and the Trigger.dev worker; without it Sentry does nothing at all. Also read at build time to enable it in the browser |
| `NEXT_PUBLIC_SENTRY_DSN`                                                                              | Optional. Only if the browser's DSN should differ from `SENTRY_DSN`; normally leave it unset |
| `SENTRY_TRACES_SAMPLE_RATE`                                                                           | Optional. Share of requests and runs that send a trace, 0 to 1 (default 0.1). Errors are always sent |
| `SENTRY_ENVIRONMENT`                                                                                  | Optional. Name shown in Sentry (default: `NODE_ENV`) |
| `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT`                                                   | Optional, for the production build only: with a token, source maps are uploaded to Sentry; without one the build is unchanged |
| `SMOKE_SECRET_CANARY`                                                                                 | Scripts only: used by `scripts/smoke-daytona.ts` to prove that a secret isn't visible inside a sandbox |
| `BILLING_PROVIDER`                                                                                    | Development only: set to `clerk` to check plans with Clerk Billing instead of the stand-in. Production always uses Clerk |
| `BILLING_STUB_PLAN`                                                                                   | Development only: set to `pro` to act as a Pro user. Ignored whenever `NODE_ENV` is `production` |
| `DAYTONA_API_KEY`                                                                                     | Optional. Daytona API key; turns on the bots' sandboxes. The SDK also reads `DAYTONA_API_URL` and `DAYTONA_TARGET` from the environment if you need a different server or region |
| `DAYTONA_SNAPSHOT`                                                                                    | Optional. The name of a Daytona snapshot to make sandboxes from. Needed only if the default sandbox image has no desktop, so computer use can't start (see `docs/computer-use.md`) |

To get the Neon variables, run `npx neon@latest login`, then `npx neon@latest link` and pick the `bro-pilot` project. The link command writes them to `.env.local`.

`npm run check:env` shows, for each place the app runs (the web server, the Trigger.dev worker, the build, scripts), which variables are set, missing or unusable. Names only, never values.

Database: edit `lib/db/schema.ts`, then run `npm run db:push` to apply it to Neon. There are no migrations; every schema change starts from a clean slate. `npm run db:studio` opens Drizzle Studio.

Tests: `npm test` runs the Vitest suite. It reads `.env.local` and uses the database in `DATABASE_URL`, creating rows under throwaway user IDs and deleting them afterwards. It never calls the real model.

Bot replies run as Trigger.dev tasks, so keep `npx trigger.dev@latest dev` running in a second terminal next to `npm run dev` (run `npx trigger.dev@latest login` once first). It reads `.env.local` too. Without it, a message is saved and its reply stays queued until the worker starts; after about five minutes it is marked as failed.

Smoke checks against real services, run by hand: `npx tsx scripts/smoke-gemini.ts` sends one real message through the model and the database, and `npx tsx scripts/smoke-trigger.ts` checks the Trigger.dev key (add `--full` with the worker running for a whole reply). `npx tsx scripts/smoke-firecrawl.ts` runs one search and reads one page (needs `FIRECRAWL_API_KEY`). If a test run is killed half-way, `npx tsx scripts/clean-test-rows.ts` removes the rows it left behind. `npx tsx scripts/smoke-sentry.ts` sends one test error to Sentry and shows that its fake key and message text were removed (needs `SENTRY_DSN`). `npx tsx scripts/smoke-daytona.ts` creates a sandbox, runs commands and files through it, stops and restarts it, and deletes it (needs `DAYTONA_API_KEY`).

Other scripts: `npm run build`, `npm run start`, `npm run lint`, `npm run typecheck` and `npm run format`. Add UI components with `npx shadcn@latest add <component>`.

## Deployment

Live on Vercel: https://bro-pilot.vercel.app (project `bro-pilot`).

Deploys are made with the Vercel CLI from a clean copy of a commit. The project isn't connected to GitHub yet, so a push doesn't deploy on its own; connect the repository in Vercel > Settings > Git to change that. For now `TRIGGER_SECRET_KEY` on Vercel is the Trigger.dev Development key, so live replies are written only while `npx trigger.dev@latest dev` is running on the developer's machine: the production worker can't be deployed yet, because Trigger.dev answers "Deployments are not available for this organization" for this account.

Sentry is optional: set `SENTRY_DSN` on Vercel (at build time too, so the browser reports) and in the Trigger.dev environment (so the worker reports); add `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT` to Vercel's build to upload source maps. Plans need Clerk Billing enabled in the Clerk dashboard, with a paid plan whose slug is `pro`; until then every user is on Free. Bot replies need two more things in production that are not set up yet: the `execute-run` task deployed to Trigger.dev (`npx trigger.dev@latest deploy`), with `DATABASE_URL` and `GOOGLE_GENERATIVE_AI_API_KEY` set in the Trigger.dev environment, and the production `TRIGGER_SECRET_KEY` set on Vercel.

### Where each variable goes

Run `npm run check:env` to see, for each place below, which of its variables are set (names only, never values). The app also logs what is missing when it starts and when it is built, and `/api/health` says whether replies, sandboxes and error tracking are on.

- **Vercel, the web server** (`*` = required): `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`*, `CLERK_SECRET_KEY`*, `DATABASE_URL`*, `TRIGGER_SECRET_KEY` (the production secret key, `tr_prod_...`; without it messages can't be sent), `DAYTONA_API_KEY` and `DAYTONA_SNAPSHOT` (sandboxes), `SENTRY_DSN`, and optionally `SENTRY_TRACES_SAMPLE_RATE`, `SENTRY_ENVIRONMENT`, the Clerk redirect paths (`NEXT_PUBLIC_CLERK_SIGN_IN_URL`, `NEXT_PUBLIC_CLERK_SIGN_UP_URL`, `NEXT_PUBLIC_CLERK_SIGN_IN_FALLBACK_REDIRECT_URL`, `NEXT_PUBLIC_CLERK_SIGN_UP_FALLBACK_REDIRECT_URL`). Never set `BILLING_STUB_PLAN` or `BILLING_PROVIDER` in production.
- **Vercel, at build time**: the two Clerk public variables above, `SENTRY_DSN` (so the browser reports errors too), and to upload source maps `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT`.
- **The Trigger.dev environment, the worker that writes replies**: `DATABASE_URL`*, `GOOGLE_GENERATIVE_AI_API_KEY`* (the model is called from here, not from Vercel), `FIRECRAWL_API_KEY` (web tools), `DAYTONA_API_KEY` and `DAYTONA_SNAPSHOT` (sandboxes), `SENTRY_DSN`, and optionally `SENTRY_TRACES_SAMPLE_RATE` and `SENTRY_ENVIRONMENT`. The worker doesn't see Vercel's variables: a key set only on Vercel does nothing for the model, the web tools or the tools in a sandbox.
- **Your machine, for scripts**: `DATABASE_URL_UNPOOLED` and `NEON_BRANCH` (for `db:push`), and any of the keys above for the smoke scripts (`SMOKE_SECRET_CANARY` is used only by `scripts/smoke-daytona.ts`).

### Deploying

1. Check it: `npm run typecheck`, `npm run lint`, `npm test` and `npm run build`.
2. If `lib/db/schema.ts` changed, apply it first with `npm run db:push` against the production database (there are no migrations; it only goes forward).
3. Deploy the worker: `npx trigger.dev@latest deploy`. The worker has its own copy of `lib/agent`, `lib/providers` and the rest of the reply code, so redeploy it whenever any of that changes, not only when `src/trigger` does.
4. Deploy the web server: `npx vercel deploy --prod` from a clean clone of the commit (`git clone --depth 1`), so no local file such as `.env.local` is uploaded; or push to `main` once the Vercel project is connected to GitHub.
5. Check `/api/health` on the live URL: `status` should be `ok`, and `features` shows what is switched on.

### Rolling back

- **Web server**: in Vercel, open the project's Deployments, pick the last good one and promote it to Production (or run `npx vercel rollback`).
- **Worker**: check out the last good commit and run `npx trigger.dev@latest deploy` again. (Trigger.dev also keeps earlier versions in its dashboard; promoting one from there hasn't been tried here.)
- **Database**: a schema change can't be rolled back (no migrations). Keep changes additive when a rollback might be needed.

### When replies fail

Work down this list; each step names where to look.

1. **Open `/api/health`.** `database: "error"` means the web server can't reach Neon (check `DATABASE_URL` on Vercel and Neon's status). `features.replies: false` means `TRIGGER_SECRET_KEY` is missing or isn't a secret key on Vercel.
2. **"Replies aren't switched on" in the chat** is the same thing: set the production `TRIGGER_SECRET_KEY` on Vercel.
3. **A reply stays on "Thinking…" and then fails with "took too long"** (after about five minutes): the worker never picked it up or died. In the Trigger.dev dashboard, open Runs and look for `execute-run`. No run: the task isn't deployed, or `TRIGGER_SECRET_KEY` belongs to a different environment than the deployed worker. A run that failed: read its error, and check that `DATABASE_URL` and `GOOGLE_GENERATIVE_AI_API_KEY` are set in that Trigger.dev environment.
4. **"The model is busy"**: Gemini returned a rate limit three times in a row. Check the quota for `GOOGLE_GENERATIVE_AI_API_KEY`; the user can press Try again.
5. **"Something went wrong with that reply"**: look in Sentry (if on) for the `runId` tag, or in the database: `select id, status, error, created_at from runs order by created_at desc limit 20;`.
6. **Bots say they can't browse**: `FIRECRAWL_API_KEY` is missing in the Trigger.dev environment (setting it only on Vercel does nothing). **Bots have no sandbox**: `DAYTONA_API_KEY` is missing on Vercel or in Trigger.dev, or the user's plan is Free.
7. **A reply stuck on "running"**: nothing to do. Runs that stop reporting are marked failed the next time anyone opens the chat or sends a message in it, and the user gets Try again.
8. **Users report "used all replies"** (HTTP 402): the plan's monthly limit; plans come from Clerk Billing (plan slug `pro`).
